# Nodus: режим «Процессы» (бизнес-процессы)

> Промпт для агента. Подаётся **по одной фазе за раз**. Перед каждой фазой агенту передаются разделы «Контекст», «Модель данных», «Общие правила» и «Чего не делать», затем текст одной фазы.
> После каждой фазы — ревью человеком и коммит. Следующая фаза стартует только после подтверждения.
> Предполагается, что `nodus-ui-rework-v3.md` выполнен: карточка — единый компонент правой панели в обоих режимах, режим «Список» — таблицы с вкладками, словари отображения типов и статусов существуют. Если что-то из этого не сделано — агент сообщает об этом в фазе 0 и не начинает фазу 1.

---

## Контекст

Nodus — сервис визуализации объектов конфигурации 1С и связей между ними. Сейчас в нём два режима:
- **Граф** — объекты (круги) и механизмы (ромбы, гиперрёбра с участниками-объектами в ролях Источник / Приёмник);
- **Список** — таблицы объектов и механизмов.

**Задача:** добавить третий режим **«Процессы»**, в котором собирается последовательная цепочка бизнес-процесса: какие объекты, реквизиты, механизмы и инструменты контроля участвуют на каждом шаге от начала процесса до конца.

**Принятые решения (не пересматривать):**
1. **Контроль** бывает двух видов:
   - **автоматический** — это существующий механизм (например, «блокируем запись, если нет остатков»); в процессе на него ссылаются, не дублируя;
   - **ручной** — новая сущность «Контроль» в общем справочнике (например, «запустить отчёт и посмотреть, где что не сходится»), переиспользуется в разных процессах.
2. **Ветвления:** линия + шаги-решения. Решение имеет 2+ исходов, ветки могут сливаться, исход может вести на более ранний шаг (возврат). Полноценный BPMN не делаем.
3. **Исполнители** — справочник ролей.
4. **Реквизиты** — заводятся вручную. Импорт из XML-выгрузки конфигурации — позже; модель должна быть к нему готова (ключ сопоставления — имя в конфигураторе).
5. **Версий процесса нет** — процесс описывает текущее состояние. Но часть механизмов «в разработке», часть «в проме», и процесс должен это явно показывать.

**Эталонный процесс для приёмки** — «Подбор персонала» (агент создаёт его в фазе 3 как тестовые данные и дополняет в следующих фазах; в итоговый коммит не входит, хранится отдельным файлом-фикстурой для импорта):
1. Руководитель создаёт заявку — создаёт `Заявка на подбор персонала`; заполняет реквизиты Подразделение, Должность, ФактическаяДатаНачалаРаботы.
2. Согласование заявки — решение: «Согласовано» → шаг 3; «На доработку» → шаг 1.
3. Система рассчитывает план закрытия — механизм `Расчёт плана закрытия заявки`; читает `Нормативный срок конкурса`; заполняет `Заявка.ПлановаяДатаЗакрытия`; изменяет `Проекты`. Контроль: ручной «Просмотр просроченных заявок в ЛК HR» (инструмент — объект `Личный кабинет HR`), реакция «информирует».
4. Система формирует движения — механизм `Движения в РН Заявки на подбор`; изменяет `РН Заявки на подбор`.
5. Рекрутер ведёт подбор — механизм `Поиск дублей физлиц` как автоматический контроль, реакция «блокирует».
6. Оформление трудоустройства — создаёт `Трудоустройство`; закрывает `Заявка на подбор персонала`; читает `Заявка.ПлановаяДатаЗакрытия`.

## Модель данных

Все новые сущности — отдельные коллекции в хранилище и отдельные опциональные разделы в формате экспорта. Существующие коллекции и поля не меняются, за исключением явно оговорённого.

```
Роль {
  id, name, description?
}

Реквизит {
  id, objectId,                 // ссылка на существующий объект
  name,                         // имя в конфигураторе — ключ для будущего импорта
  synonym?, valueType?,
  tabularSection?,              // имя табличной части; пусто = реквизит шапки
  description?
}

Контроль (ручной) {
  id, name,
  instruction,                  // что сделать и на что смотреть
  toolObjectId?,                // объект-инструмент: отчёт, обработка, ЛК
  responsibleRoleId?,
  moment,                       // "on_step" | "periodic" | "on_event"
  momentNote?,                  // "ежедневно", "при закрытии месяца"
  replacedByMechanismId?,       // механизм, который заменит этот ручной контроль
  status                        // из того же словаря статусов, что у объектов
}

Процесс {
  id, name, description?, subsystem?, ownerRoleId?,
  startStepId,
  steps: Шаг[]
}

Шаг {
  id, name, description?,
  kind,                         // "user_action" | "auto_action" | "decision" | "event"
  roleId?,                      // для auto_action допустимо пусто = «Система»
  next,                         // id шага или null; для decision не используется
  outcomes?: [{ id, label, next }],   // только для decision, 2+
  participants: [{
    entityType,                 // "object" | "attribute" | "mechanism"
    entityId,
    role,                       // см. таблицу ролей ниже
    note?
  }],
  controls: [{
    source,                     // "mechanism" | "manual"
    sourceId,                   // id механизма или ручного контроля
    targets: [{ entityType: "object" | "attribute", entityId }],
    reaction,                   // "block" | "warn" | "inform"
    note?
  }]
}
```

**Роли участников шага:**

| entityType | role | Буква в матрице |
|---|---|---|
| object | `create` создаёт | С |
| object | `update` изменяет | И |
| object | `read` читает | Ч |
| object | `post` проводит | П |
| object | `close` закрывает | Х |
| attribute | `fill` заполняет | З |
| attribute | `update` изменяет | И |
| attribute | `read` читает | Ч |
| mechanism | `run` запускается | — |
| mechanism | `auto` срабатывает автоматически | — |

Контроль в матрице обозначается буквой **К** в ячейках своих `targets`.

**Порядок шагов** задаётся только ссылками `next` / `outcomes[].next`. Массив `steps` — неупорядоченное хранилище. Порядок отображения вычисляется (см. фазу 5).

**Готовность («в проме»):** ввести константу-множество `READY_STATUSES` — значения статуса, считающиеся «в проме» (по итогам фазы 0; для объектов ожидается «В проме», для механизмов — значение, соответствующее «в проме» в их словаре). Всё, что не входит в множество и не «устаревшее», считается «в разработке».

## Общие правила (для всех фаз)

- **Работай в существующем стеке и структуре файлов.** Ленту, дорожки и матрицу рисовать средствами текущего стека (HTML/SVG). Новую зависимость — только с обоснованием в отчёте и только если без неё задача требует >150 строк своего кода.
- **Обратная совместимость.** Данные и файлы экспорта, созданные до фазы, открываются без ошибок и потерь. Файл экспорта без новых разделов импортируется как «процессов, ролей, реквизитов и контролей нет».
- **Переиспользование компонентов.** Правая панель карточки, комбобокс поиска сущностей, бейджи типа и статуса, индикатор сохранения, inline-редактирование, меню «⋯» — существующие компоненты. Новая копия компонента запрещена.
- **Токены.** Цвета, размеры, прозрачности — только через токены; новые токены добавляются в файл токенов.
- **Идентификаторы** новых сущностей генерируются тем же способом, что у существующих.
- **Ссылочная целостность:** при удалении любой сущности, на которую ссылается процесс (объект, реквизит, механизм, роль, контроль), — предупреждение со списком процессов и шагов. После подтверждения ссылка в шаге остаётся «битой» и отображается как «⚠ Удалено: <последнее известное название>», а не исчезает.
- **Никаких изменений вне скоупа фазы.** Замеченные баги — в отчёт, не чинить.
- **Проверка перед сдачей каждой фазы:**
  - синтаксическая проверка изменённых JS/TS (`node --check` для JS или сборка без ошибок);
  - сверка: каждый `id`/селектор из JS существует в разметке и наоборот;
  - консоль браузера без новых ошибок при сценарии фазы (описан в её критериях);
  - экспорт → очистка → импорт: все данные, включая новые разделы, восстанавливаются полностью;
  - импорт экспорта, сделанного до фазы, проходит без ошибок.
- **Отчёт по фазе:** изменённые файлы; что сделано по каждому пункту; какие критерии приёмки проверены и как; отклонения и причины; баги вне скоупа.

## Чего не делать (для всех фаз)

- Не менять модель механизма как гиперребра и роли его участников.
- Не переименовывать и не удалять существующие поля и коллекции.
- Не менять физику графа и поведение режимов «Граф» и «Список», кроме явно оговорённых точек интеграции.
- Не делать версии процесса (as-is / to-be), историю изменений, параллельные ветки (AND-split), таймеры, подпроцессы.
- Не делать импорт реквизитов из XML-выгрузки конфигурации.
- Не делать экспорт процесса в BPMN, PNG, PDF.
- Не добавлять анимаций длиннее 250 мс.
- Не начинать следующую фазу в рамках текущей.

## Фаза 1. Справочники: роли и реквизиты

**Задача:** завести две новые сущности, которые понадобятся процессам.

**Сделать:**
1. **Роли:**
   - коллекция и раздел экспорта;
   - в режиме «Список» новая вкладка «Роли»: таблица (Название | Описание | Используется в процессах — пока всегда 0), «+ Роль», карточка в правой панели (inline-редактирование названия и описания, удаление через «⋯»);
   - название роли уникально без учёта регистра; дубль не сохраняется, показывается ошибка.
2. **Реквизиты:**
   - коллекция и раздел экспорта;
   - в карточке объекта новый блок **«Реквизиты · N»** между «Участвует в механизмах» и «Описанием»: компактная таблица (Имя | Синоним | Тип), группировка по табличным частям (сначала «Шапка», затем табличные части по алфавиту), сворачиваемые группы;
   - добавление строкой внизу таблицы: поля имя (обязательное), синоним, тип значения, табличная часть (комбобокс из уже существующих табличных частей этого объекта + создание новой); `Enter` сохраняет и открывает следующую пустую строку;
   - редактирование по клику на ячейку, удаление через «⋯» строки;
   - валидация имени: без пробелов и точек, не начинается с цифры, уникально в пределах объекта и табличной части (без учёта регистра);
   - полное имя реквизита для отображения: `<Имя объекта в конфигураторе>.<Имя реквизита>` или `<…>.<ТабличнаяЧасть>.<Имя реквизита>`.
3. При удалении объекта с реквизитами — в существующем подтверждении указать число реквизитов; реквизиты удаляются вместе с объектом.
4. Счётчик реквизитов показывается в колонке «Реквизиты» в таблице объектов режима «Список» (колонка скрывается первой при нехватке ширины).

**Не делать:** ручные контроли (фаза 2), что-либо, связанное с процессами.

**Критерии приёмки:**
- Можно создать роли «Руководитель», «Рекрутер», «HR BP»; дубль «руководитель» не создаётся.
- У объекта «Заявка на подбор персонала» можно ввести 4 реквизита шапки подряд, не касаясь мыши (только `Tab` и `Enter`).
- Реквизит `Кандидаты.ФИО` отображается в группе табличной части «Кандидаты».
- Реквизит с именем `1Дата` или `Плановая дата` не сохраняется, ошибка видна под полем.
- Экспорт → очистка → импорт восстанавливает роли и реквизиты полностью.

## Фаза 3. Процесс и линейная лента шагов

**Задача:** третий режим с редактором процесса. Только линейные процессы; шаги-решения — в фазе 5.

**Сделать:**
1. **Режим:** переключатель верхней панели «Граф / Список / Процессы». Выбранный процесс сохраняется при переключении режимов и перезагрузке, как выбранный объект.
2. **Левая панель режима:** поиск, фильтр по подсистеме, список процессов (название, число шагов), «+ Процесс». Создание: процесс «Новый процесс» с одним пустым шагом, открыт в центре, карточка процесса в правой панели с фокусом в названии.
3. **Карточка процесса** (правая панель, когда не выбран шаг): название, описание, подсистема (тот же комбобокс, что у объекта), владелец (комбобокс ролей), счётчики шагов, удаление через «⋯».
4. **Лента (центр):** карточки шагов слева направо в порядке `next` от `startStepId`, соединены стрелками, горизонтальная прокрутка и зум (колесо + `Ctrl`), кнопка «Вписать».
5. **Карточка шага на ленте** (ширина фиксированная, 240px ± 20):
   - строка 1: порядковый номер (вычисляется), название;
   - строка 2: роль (иконка человека) или «Система» (иконка шестерёнки) для `auto_action` без роли;
   - далее группы чипов: механизмы (ромб в цвете категории), объекты и реквизиты (точка цвета типа объекта; реквизит — `Объект · Реквизит`), по одной строке на группу; если не помещается — «+N».
   - чип показывает роль участия буквой из таблицы ролей (С, И, Ч, П, Х, З).
6. **Добавление шага:** «+» на стрелке между карточками вставляет шаг между ними; «+» после последней карточки добавляет в конец. Удаление шага (через «⋯» карточки) сшивает `next` предыдущего с последующим.
7. **Перестановка:** в меню «⋯» карточки — «Сдвинуть влево / вправо».
8. **Карточка шага (правая панель)** по клику на карточку:
   - шапка: номер, название (inline), бейдж вида шага (смена по клику; в этой фазе доступны `user_action`, `auto_action`, `event`), роль (комбобокс с созданием роли);
   - описание;
   - **Участники** — сгруппированы: Механизмы / Объекты / Реквизиты; добавление через существующий комбобокс поиска, после выбора — выбор роли участия из допустимых для типа (таблица ролей); примечание;
   - при добавлении реквизита — комбобокс ищет по `Объект.Реквизит`; пункт «+ Создать реквизит у объекта …» создаёт его без перехода (объект выбирается, если не выбран);
   - клик по участнику — открывает его карточку (с возвратом к шагу кнопкой «← К шагу»).
9. **Ссылочная целостность** (из общих правил) для объектов, реквизитов, механизмов и ролей, используемых в шагах.
10. Эталонный процесс «Подбор персонала» (шаги 1, 3, 4, 5, 6 из «Контекста» — без решения и без контролей) сохранить как фикстуру.

**Не делать:** решения и исходы, контроли, статусы готовности, матрицу, дорожки.

**Критерии приёмки:**
- Эталонный процесс собирается целиком через интерфейс; в отчёте — число кликов на добавление одного участника (ожидается ≤ 4: «+», поиск, выбор, роль).
- Вставка шага между 2 и 3 перенумеровывает шаги; `next` в данных корректны (проверить по экспорту).
- Удаление объекта, участвующего в шаге, оставляет в шаге чип «⚠ Удалено: …».
- Переключение Процессы → Граф → Процессы возвращает к тому же процессу и шагу.
- 10 шагов на ленте прокручиваются и вписываются кнопкой «Вписать» без наложения карточек.

## Фаза 4. Контроли в шагах и готовность

**Задача:** привязать контроли к шагам и показать, что в проме, а что в разработке.

**Сделать:**
1. **Контроли в карточке шага (правая панель):** раздел «Контроли · N», кнопка «+ Контроль» → выбор источника:
   - «Механизм» — комбобокс механизмов (категория «Проверка» — первой группой в выпадающем списке);
   - «Ручной» — комбобокс ручных контролей с пунктом «+ Создать контроль „…“» (создаёт и открывает для заполнения после привязки);
   затем: цели (объекты и реквизиты — по умолчанию предлагаются участники шага), реакция (сегмент «Блокирует / Предупреждает / Информирует»; для ручного по умолчанию «Информирует»), примечание.
2. **На ленте:** группа чипов контролей с иконкой щита; автоматический — щит сплошной, ручной — щит контурный; буква реакции (Б / П / И).
3. **Готовность** (по `READY_STATUSES`):
   - чип участника или контроля «в разработке» — контурный с штриховкой (токен), подсказка «В разработке»;
   - индикатор у номера шага: ● все механизмы и автоматические контроли шага в проме; ◐ часть в разработке; ○ все в разработке; шаг без механизмов и контролей — без индикатора;
   - в шапке процесса и в левом списке процессов: «Готово N из M шагов».
4. **Переключатель «Только в проме»** над лентой: приглушает (35%) чипы «в разработке»; шаги, у которых после этого не осталось ни механизмов, ни контролей, помечаются «ручная работа» (бейдж).
5. Ручной контроль с заполненным `replacedByMechanismId` показывает на чипе и в карточке шага метку «временный → <механизм>».
6. Обратные ссылки: блок «Используется в процессах» в карточке ручного контроля (процесс · шаг · реакция) заполняется.

**Не делать:** проверки процесса (фаза 6).

**Критерии приёмки:**
- В эталонном процессе шагу 3 добавлен ручной контроль из фазы 2, шагу 5 — механизм `Поиск дублей физлиц` с реакцией «Блокирует»; оба видны на ленте с правильными иконками и буквами.
- Перевод механизма `Расчёт плана закрытия заявки` в статус «в разработке» меняет индикатор шага 3 на ○/◐ и счётчик «Готово N из M» без перезагрузки.
- «Только в проме» при механизме шага 4 в разработке помечает шаг 4 «ручная работа».
- Контроль, привязанный к шагу, нельзя удалить из справочника без предупреждения со списком шагов.

## Фаза 5. Решения, ветки, возвраты

**Задача:** шаг-решение с исходами, ветвление и слияние ленты, возвраты.

**Сделать:**
1. **Вид шага `decision`** доступен в бейдже вида. Карточка на ленте — с ромбовидной меткой вида. При переводе шага в `decision` его `next` становится первым исходом «Да» (или подписью по умолчанию «Исход 1»), создаётся второй пустой исход.
2. **Исходы в карточке шага:** раздел «Исходы», у каждого — подпись и цель: «Новая ветка» (создаёт пустой шаг) / «К существующему шагу» (комбобокс шагов процесса) / «Завершение процесса». Добавление и удаление исходов; минимум 2.
3. **Раскладка ленты** (детерминированная, вычисляется при каждом изменении):
   - обход в глубину от `startStepId`; переход к шагу, который уже находится на текущем пути обхода, считается **возвратом**;
   - колонка шага = длина самого длинного пути от старта без учёта возвратов;
   - первый исход решения продолжает строку решения, остальные — строки ниже; строка ветки при слиянии завершается стрелкой к шагу слияния;
   - возвраты рисуются дугой **над** лентой с подписью исхода;
   - нумерация шагов — по колонке, внутри колонки — по строке (например, 4, 4а, 4б для шагов одной колонки в разных ветках).
4. **Добавление шага** «+» на стрелке ветки вставляет шаг в эту ветку; удаление шага в ветке сшивает ветку.
5. Удаление шага, на который ведут другие ссылки (исходы или `next` из других веток), — подтверждение со списком ссылающихся шагов; ссылки переводятся на следующий шаг удаляемого или на «Завершение процесса», если следующего нет.
6. Добавить в эталонный процесс шаг 2 «Согласование заявки» (решение: «Согласовано» → шаг 3; «На доработку» → шаг 1).

**Не делать:** параллельные ветки (выполнение нескольких веток одновременно), вложенные подпроцессы, перетаскивание карточек мышью.

**Критерии приёмки:**
- Эталонный процесс: возврат «На доработку» рисуется дугой над лентой от шага 2 к шагу 1 с подписью; «Согласовано» ведёт к шагу 3 в той же строке.
- Процесс с решением на 3 исхода, где 2 ветки по 2 шага сливаются в общий шаг: карточки не перекрываются, стрелки слияния не пересекают карточки (проверить визуально и приложить скриншот к отчёту).
- Раскладка стабильна: повторная загрузка того же процесса даёт идентичные позиции карточек.
- Удаление шага, на который ведёт исход, не оставляет в данных ссылок на несуществующий `id` (проверить по экспорту).

## Фаза 6. Матрица и проверки процесса

**Задача:** показать жизненный цикл объектов и реквизитов по шагам и автоматически находить проблемы.

**Сделать:**
1. **Переключатель вида** над лентой: «Лента | Матрица» (дорожки добавятся в фазе 7).
2. **Матрица:**
   - столбцы — шаги в порядке раскладки (номера как на ленте), заголовок столбца — номер и название (обрезка, полное — в tooltip), закреплён при вертикальной прокрутке;
   - строки — объекты; под каждым объектом — его реквизиты, участвующие в процессе (сворачиваемо), первый столбец закреплён при горизонтальной прокрутке;
   - ячейка — буквы ролей участия (С, И, Ч, П, Х, З) и **К**, если шаг контролирует объект/реквизит; несколько букв — через пробел;
   - ячейки с **К** выделены фоном токена контроля; клик по ячейке открывает карточку шага;
   - строки и столбцы с участниками «в разработке» — со штриховкой заголовка.
3. **Проверки процесса** — вычисляются при каждом изменении, по всем путям от старта (возвраты не повторяются):
   - **Чтение до заполнения:** на каком-либо пути реквизит читается (`read`) на шаге раньше, чем заполняется (`fill`) — предупреждение на шаге чтения;
   - **Заполнен, но не используется:** реквизит заполняется и далее ни на одном пути не читается и не контролируется — предупреждение на шаге заполнения;
   - **Изменяется без контроля:** объект создаётся или изменяется, но ни на одном шаге процесса нет контроля, целью которого является он или его реквизит — предупреждение на объекте (в матрице — на заголовке строки);
   - **Структура:** у решения < 2 исходов; у `user_action` нет роли; шаг недостижим от старта; путь не ведёт к завершению (бесконечный цикл без выхода);
   - **Готовность:** шаг опирается на механизм «в разработке», и на шаге нет ручного контроля — информационное сообщение.
4. **Отображение проверок:** иконка ⚠ (предупреждение) или ⓘ (информация) на карточке шага и в ячейке матрицы; в шапке процесса — «Проблем: N», по клику — панель со списком (текст проблемы, шаг, переход к шагу по клику).
5. Проверки не блокируют сохранение.

**Не делать:** автоисправление проблем, настройку правил проверок.

**Критерии приёмки:**
- Эталонный процесс: строка `Заявка.ПлановаяДатаЗакрытия` показывает **З** на шаге 3 и **Ч** на шаге 6.
- Если перенести чтение `ПлановаяДатаЗакрытия` на шаг 1 — появляется предупреждение «чтение до заполнения» на шаге 1; после возврата — исчезает.
- Удаление всех контролей, нацеленных на `РН Заявки на подбор`, даёт предупреждение «изменяется без контроля» для этого объекта.
- Недостижимый шаг (созданный как цель исхода, а затем отвязанный) даёт структурное предупреждение.
- Пересчёт проверок на процессе из 30 шагов с 3 решениями занимает < 100 мс (указать замер).

## Фаза 7. Дорожки, наложение на граф, обратные связи

**Задача:** связать режим «Процессы» с остальным Nodus.

**Сделать:**
1. **Вид «Дорожки»** в переключателе «Лента | Дорожки | Матрица»: те же карточки и колонки, что на ленте, но строка карточки определяется ролью шага; дорожка «Система» — для `auto_action` без роли. Заголовки дорожек закреплены слева. Ветки внутри одной дорожки — подстроки. Возвраты — дугами над своей дорожкой. Порядок дорожек — по первому появлению роли в процессе.
2. **Наложение на граф:** в режиме «Граф» в левой панели — выбор «Процесс: <нет | список>». При выбранном процессе:
   - узлы, не участвующие в процессе, приглушены до уровня «фон» (существующий токен);
   - на участвующих объектах и механизмах — бейдж с номерами шагов (например, «1, 6»; если > 3 — «1, 3 +2»);
   - клик по бейджу открывает режим «Процессы» на первом из этих шагов.
3. **Обратные блоки в карточках:**
   - объект: «Участвует в процессах · N» — процесс · номер шага · роли участия (включая роли его реквизитов и контроли, нацеленные на него); клик — переход к шагу;
   - механизм: «Используется в процессах · N» (участник) и «Контролирует в процессах · N» (источник контроля);
   - роль: счётчик «Используется в процессах» в таблице и список в карточке становятся реальными.
4. **Колонка «Процессы»** в таблицах объектов и механизмов режима «Список» (число; скрывается при нехватке ширины после «Тегов»).
5. **Поиск `Ctrl+K`** находит процессы и шаги (результат «Шаг 3 · Подбор персонала»); выбор открывает режим «Процессы» на этом шаге.

**Не делать:** редактирование процесса из режима «Граф», отображение порядка шагов стрелками на графе.

**Критерии приёмки:**
- Эталонный процесс в дорожках: 3 дорожки (Руководитель, Система, Рекрутер) + дорожка роли шага 6, если она отличается; шаги 3 и 4 — в дорожке «Система».
- Наложение эталонного процесса на граф: `Заявка на подбор персонала` показывает бейдж «1, 6», объекты вне процесса приглушены; сброс выбора возвращает граф в исходное состояние.
- Карточка `Заявка на подбор персонала` показывает «Участвует в процессах · 1» с шагами 1 (С, З) и 6 (Х, Ч).
- `Ctrl+K` → «Согласование» находит шаг 2 и открывает его.
- Экспорт → очистка → импорт после всех фаз восстанавливает эталонный процесс полностью, включая раскладку ленты (идентичные позиции).
