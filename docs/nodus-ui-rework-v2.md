# Nodus v0.3 → v0.4: переработка UI (читаемость и юзабилити)

> Промпт для агента. Подаётся **по одной фазе за раз**. Каждая фаза самодостаточна: перед ней агенту передаются разделы «Контекст», «Общие правила» и «Чего не делать», затем текст одной фазы.
> После каждой фазы — ревью человеком и коммит. Следующая фаза стартует только после подтверждения.

---

## Контекст

Nodus — сервис визуализации объектов конфигурации 1С и связей между ними.

**Модель данных (двухслойная):**
- **Объект** — справочник, документ, регистр и т.п. Узел графа (круг).
- **Механизм** — именованное правило, связывающее несколько объектов (гиперребро). Узел графа (ромб). Поля: заголовок, категория (Заполнение, Проверка, …), статус, краткое описание (подсказка на графе), подробное описание, участники, вложения.
- **Участник механизма** — ссылка на объект + роль (Источник / Приёмник) + текстовое описание того, что передаётся («Источник к-ва дней», «Забирает к-во дней»).

**Текущий экран:**
- Верхняя панель: переключатель «Граф / Список», переключатель «Объекты / Объекты и механизмы», кнопки «Настройки», «Разложить заново», «Экспорт», «Импорт», «Очистить всё».
- Левая панель: вкладки «Объекты N / Механизмы N», поле «Название механизма» + кнопка «+» (создание), фильтр категорий, список.
- Центр: force-directed граф. Hover подсвечивает связи, клик закрепляет подсветку и открывает карточку, клик по пустому месту снимает.
- Правая панель: карточка выбранного механизма (или объекта).

**Выявленные проблемы, которые решает эта переработка:**
1. Приглушённые узлы почти невидимы, контекст теряется.
2. Роли участников не видны на графе — только в правой панели.
3. Подписи узлов перекрываются.
4. Цвет узлов ничего не кодирует, легенды нет.
5. Деструктивное «Очистить всё» стоит в одном ряду с рядовыми действиями.
6. Поле создания механизма выглядит как поиск.
7. Правая панель: дублирование заголовка, обрезанные имена участников, 3 контрола на участника, вложенный скролл описания, нет индикатора сохранения.
8. Мелкий шрифт и низкий контраст вторичного текста.

## Общие правила (для всех фаз)

- **Стек определяется фазой 0.** Работай в существующем стеке и структуре файлов, не вводи новых фреймворков. Новую зависимость — только с явным обоснованием в отчёте и только если без неё задача требует >150 строк своего кода.
- **Обратная совместимость данных.** Существующие сохранённые данные и файлы экспорта должны открываться без ошибок и без потерь. Новые поля данных — только опциональные, со значением по умолчанию.
- **Никаких изменений поведения вне скоупа фазы.** Если заметил баг вне скоупа — опиши в отчёте, не чини.
- **Все цвета, размеры шрифтов и прозрачности — через токены** (CSS-переменные / константы темы), введённые в фазе 1. Хардкод новых значений запрещён.
- **Проверка перед сдачей каждой фазы:**
  - синтаксическая проверка всех изменённых JS/TS-файлов (`node --check` для JS или сборка без ошибок для TS/React);
  - сверка: каждый `id`/селектор, на который ссылается JS, существует в разметке, и наоборот — нет «мёртвых» обработчиков;
  - консоль браузера без новых ошибок и предупреждений при сценарии: загрузка → выбор механизма → выбор объекта → редактирование → снятие выделения.
- **Отчёт по фазе** (в конце ответа): список изменённых файлов; что сделано по каждому пункту; какие критерии приёмки проверены и как; отклонения от задания и почему; замеченные баги вне скоупа.

## Чего не делать (для всех фаз)

- Не менять модель данных механизма как гиперребра (не превращать в парные рёбра).
- Не переименовывать и не удалять существующие поля в сохранённых данных и формате экспорта.
- Не менять алгоритм физики графа, кроме явно оговорённого в фазе 6.
- Не переделывать режим «Список» — он вне скоупа.
- Не делать редизайн «с нуля»: сохраняй тёмную тему, общую раскладку «левая панель / холст / правая панель» и существующие сценарии взаимодействия.
- Не добавлять анимаций длиннее 250 мс.
- Не начинать следующую фазу в рамках текущей.

## Фаза 0. Разведка (без изменений кода)

**Задача:** изучить кодовую базу и подготовить карту для последующих фаз.

**Сделать:**
1. Определить стек и точку входа, способ рендеринга графа (библиотека, canvas/SVG/WebGL).
2. Найти, где задаются: цвета, шрифты, прозрачность приглушённых узлов, стиль рёбер, отрисовка подписей.
3. Найти структуру объекта, механизма и участника в коде и в сохранённых данных. Ответить: **есть ли у объекта поле типа** (справочник/документ/регистр)? Какие значения ролей существуют (только Источник/Приёмник или больше)?
4. Найти обработчики: создания механизма, «Очистить всё», импорта/экспорта, сохранения карточки.
5. Выяснить, как сохраняются изменения карточки (автосохранение по input/blur, кнопка, debounce?).

**Не делать:** любые изменения файлов.

**Критерии приёмки:**
- Отчёт содержит ответы на все 5 пунктов со ссылками на файлы и строки.
- Явно указано, есть ли поле типа объекта и полный список значений ролей.
- Перечислены риски для фаз 1–6 (например: «подписи рисует библиотека, коллизии придётся делать своим слоем»).

## Фаза 1. Токены, типографика, контраст

**Задача:** ввести систему токенов и поднять читаемость текста. Визуальный язык сохраняется.

**Сделать:**
1. Вынести в токены: цвета фона (3 уровня: холст, панель, поле ввода), цвета текста (основной, вторичный, приглушённый), акцент, цвет опасного действия, цвета категорий механизмов, цвета типов объектов, прозрачности узлов (активный / сосед / фоновый), размеры шрифтов.
2. Типографика:
   - базовый текст интерфейса — 13px;
   - вторичный текст (подписи полей, категория в списке, подсказки) — не меньше 12px;
   - подписи узлов на графе — не меньше 12px.
3. Контраст: осветлить вторичный серый так, чтобы проходил WCAG AA.
4. Акцентный цвет закрепить за **выделением и связями на графе**. Активная вкладка / активный сегмент переключателя — нейтральный светлый фон с основным цветом текста, а не акцентный.
5. Подсказку внизу холста («Наведите — подсветит связи…») сделать читаемой: вторичный цвет текста, 12px.

**Не делать:** менять раскладку, отступы блоков, логику.

**Критерии приёмки:**
- В изменённых файлах нет новых хардкод-цветов (`#…`, `rgb(…)`) вне файла/блока токенов — проверяется поиском.
- Контраст основного текста к фону ≥ 7:1, вторичного ≥ 4.5:1 (указать измеренные значения в отчёте).
- Ни один текстовый элемент интерфейса не меньше 12px (проверка по computed styles или по токенам).
- Активная вкладка «Механизмы» и активный режим «Граф» визуально отличимы от неактивных без использования акцентного цвета.

## Фаза 2. Верхняя панель и безопасность действий

**Задача:** разгрузить верхнюю панель и защитить деструктивное действие.

**Сделать:**
1. Переключатель «Объекты / Объекты и механизмы» заменить на переключатель-чекбокс **«Показывать механизмы»** (включён = текущее «Объекты и механизмы»). Состояние сохраняется так же, как сейчас.
2. «Экспорт», «Импорт», «Очистить всё» перенести в меню **«⋯»** в правой части верхней панели. «Очистить всё» — последний пункт, отделён разделителем, цвет опасного действия.
3. «Очистить всё» открывает модальное окно подтверждения:
   - текст с количеством: «Будет удалено N объектов, M механизмов и K вложений. Действие необратимо.»;
   - кнопка удаления неактивна, пока пользователь не введёт слово `удалить`;
   - в окне есть кнопка «Сначала сделать экспорт», вызывающая существующий экспорт.
4. «Разложить заново» убрать из верхней панели — она переедет к холсту в фазе 4. **До фазы 4 временно оставить её в меню «⋯»**, чтобы функция не пропала.
5. В освободившемся центре верхней панели — поле **глобального поиска** по объектам и механизмам: выпадающий список совпадений (подстрока, без учёта регистра), выбор результата = то же действие, что клик по узлу. Горячая клавиша `Ctrl+K` / `Cmd+K` фокусирует поле, `Esc` закрывает список.

**Не делать:** менять логику экспорта/импорта/очистки — только точку входа.

**Критерии приёмки:**
- В верхней панели видимых кнопок-действий не больше двух (Настройки, «⋯»), не считая переключателей и поиска.
- Очистку невозможно выполнить без ввода слова `удалить` — проверено вручную; `Esc` и клик вне окна закрывают его без удаления.
- Числа в окне подтверждения совпадают с фактическим количеством сущностей.
- Поиск находит объект и механизм по части названия; `Enter` / клик выбирает, граф центрируется на узле (если центрирование ещё не реализовано — достаточно выделения, центрирование придёт в фазе 4).
- Экспорт, импорт, «Разложить заново» работают как раньше.

## Фаза 3. Левая панель

**Задача:** разделить поиск и создание, сделать список информативным.

**Сделать:**
1. Поле «Название механизма» + «+» заменить на:
   - **поле фильтра списка** (placeholder «Поиск механизмов…» / «Поиск объектов…» в зависимости от вкладки), фильтрует мгновенно;
   - кнопку **«+ Механизм»** / **«+ Объект»** в заголовке вкладки. Нажатие создаёт сущность с названием «Новый механизм» и сразу открывает её карточку справа с фокусом в поле названия.
2. Фильтр категорий оставить, разместить под полем поиска.
3. Маркер-ромб в строке списка окрасить в цвет категории (токены из фазы 1). Тот же цвет — у ромба на графе (фаза 4).
4. Категорию под названием отображать бейджем (цвет категории, фон с прозрачностью ~15%), а не серым текстом.
5. Справа в строке механизма — число участников. Если у механизма нет ни одного источника или ни одного приёмника — иконка предупреждения с tooltip «Нет источника» / «Нет приёмника».
6. Если у механизма пустое краткое описание — маленький индикатор «без описания» (приглушённый), чтобы было видно, что подсказка на графе пустая.
7. Hover по строке списка подсвечивает соответствующий узел на графе (как hover по узлу), уход курсора — снимает. Клик — как клик по узлу.
8. Для вкладки «Объекты» — аналогично: иконка типа объекта (фаза 4, до неё — нейтральный кружок) и число механизмов, в которых объект участвует.

**Не делать:** группировку списка по категориям со сворачиванием (отложено), drag-and-drop.

**Критерии приёмки:**
- Нажатие `Enter` в поле поиска **не создаёт** сущность.
- Создание: 1 клик → новая сущность в списке, карточка открыта, курсор в поле названия.
- Цвет маркера в списке совпадает с цветом категории (один токен на категорию).
- Механизм без приёмника показывает предупреждение; после добавления приёмника предупреждение исчезает без перезагрузки.
- Hover по строке меняет подсветку на графе с задержкой < 100 мс, без мерцания.

## Фаза 4. Читаемость графа

**Задача:** сделать граф читаемым без правой панели.

**Сделать:**
1. **Три уровня прозрачности** при активном выделении:
   - выделенный узел и прямые участники — 100%;
   - соседи второго порядка (другие механизмы тех же объектов и их участники) — 55%;
   - остальное — 35%.
   Подписи фоновых узлов — не ниже 45% (читаемы, но не конкурируют).
   Без выделения всё — 100%.
2. **Подложка под подписи:** плашка цвета холста с прозрачностью ~85% и скруглением 3px. Подпись механизма — **над** ромбом, объекта — под кругом.
3. **Коллизии подписей:** если прямоугольники подписей пересекаются, подпись узла с меньшим приоритетом скрывается. Приоритет: выделенный > участник выделенного > hover > узел с большей степенью > остальные. Скрытая подпись показывается при hover.
4. **Тип объекта:** внутри круга — короткая метка типа (`Сп`, `Док`, `РН`, `РС`, `РБ`, `Пер`…; итоговый список согласно фазе 0). Цвет круга — по типу (токены). Если поля типа нет — добавить опциональное поле `type` со значением по умолчанию `unknown` (нейтральный цвет, без метки) и выпадающий список «Тип» в карточке объекта.
5. **Ромб механизма** — цвет категории.
6. **Легенда** в левом нижнем углу холста: типы объектов и категории механизмов, сворачивается в кнопку. Показываются только реально присутствующие типы/категории.
7. **Стиль рёбер по роли:** источник → механизм — сплошная линия; механизм → приёмник — пунктир. Стрелки сохраняются. Неизвестные роли (если есть по итогам фазы 0) — точечная линия.
8. **Контролы холста** в правом нижнем углу: `+`, `–`, «вписать в экран», «разложить заново» (перенесена из меню «⋯» — там удалить).
9. **Центрирование:** выбор узла из списка или поиска плавно (≤ 250 мс) центрирует холст на узле, если он вне видимой области или ближе 80px к краю.

**Не делать:** менять физику раскладки; подписи на рёбрах (это фаза 6); мини-карту (фаза 6).

**Критерии приёмки:**
- На тестовых данных (12 объектов, 5 механизмов) при выделении любого механизма **все** подписи его участников видны и не пересекаются друг с другом.
- Без выделения на экране нет пересекающихся видимых подписей (проверить на тестовых данных и на наборе из ≥ 40 узлов — сгенерировать временно, в коммит не включать).
- Подпись фонового узла при активном выделении читается (контраст подписи к фону ≥ 3:1 — указать значение).
- Легенда отражает ровно те типы и категории, что есть в данных; добавление объекта нового типа добавляет пункт в легенду.
- Старые данные без поля `type` открываются, узлы отображаются нейтральным цветом, ошибок нет.
- «Вписать в экран» показывает все узлы с отступом ≥ 40px от краёв холста.

## Фаза 5. Правая панель (карточка механизма и объекта)

**Задача:** сделать карточку компактной и связанной с графом.

**Сделать:**
1. **Заголовок:** убрать поле «Заголовок». Крупный заголовок карточки редактируется inline по клику (`Enter` / blur — сохранить, `Esc` — отменить). Пустое название не сохраняется (возврат к предыдущему, короткое сообщение).
2. **Участники сгруппированы по ролям:** блоки «Источники» и «Приёмники» (плюс блок для каждой прочей роли, если есть). Выпадающий список роли у каждого участника убрать; смена роли — через меню участника «⋯ → Сделать приёмником / источником».
3. **Кнопка добавления** — в заголовке каждого блока («+ источник», «+ приёмник»), открывает существующий комбобокс поиска объекта.
4. **Карточка участника** (одна строка + описание):
   - иконка/метка типа объекта (из фазы 4);
   - полное имя объекта **с переносом, без обрезки**;
   - описание передачи вторичным текстом под именем; редактирование по клику inline;
   - меню «⋯»: сменить роль, удалить.
   - клик по имени — выделяет и центрирует объект на графе, открывает его карточку.
   - hover по карточке участника подсвечивает соответствующее ребро на графе.
5. **Подробное описание:**
   - режим просмотра по умолчанию: текст с сохранением переносов и нумерации; фрагменты `[Название]`, совпадающие с названием существующего объекта (без учёта регистра), рендерятся **чипами-ссылками** — клик = переход к объекту, hover = подсветка на графе; несовпавшие — обычный текст в скобках;
   - клик по тексту / кнопка «Редактировать» — textarea с автоувеличением высоты (без внутреннего скролла до 60% высоты панели);
   - формат хранения описания не меняется (плоский текст).
6. **Краткое описание:** placeholder «Одна фраза: что делает механизм. Показывается при наведении на граф».
7. **Индикатор сохранения** возле заголовка: «Сохранено» / «Сохранение…» / «Ошибка сохранения» (цвет опасного действия, с кнопкой «Повторить»). Механика сохранения — прежняя (по итогам фазы 0).
8. «Удалить механизм» — оставить внизу, добавить подтверждение с названием механизма.
9. Карточку объекта привести к тому же стилю: inline-заголовок, поле «Тип», список механизмов, в которых участвует объект, с ролью и кликом-переходом.

**Не делать:** менять логику вложений; менять формат хранения описания; вводить rich-text/markdown-редактор.

**Критерии приёмки:**
- На ширине панели по умолчанию имя «Заявка на подбор персонала» отображается полностью.
- Один участник занимает по вертикали не больше 2 строк текста + отступы (в режиме просмотра).
- Смена роли участника: ≤ 2 клика, участник переезжает в другой блок, направление ребра на графе меняется сразу.
- `[Заявки на подбор персонала]` в описании — кликабельный чип, клик выделяет объект; `[Несуществующий]` — обычный текст.
- Экспорт механизма после правок в фазе 5 побайтово совпадает по структуре с экспортом до неё (отличаются только изменённые значения).
- Индикатор показывает «Сохранено» не позже 1 с после окончания ввода.

## Фаза 6. Фокус-режим механизма и навигация

**Задача:** быстрый разбор одного механизма как потока данных.

**Сделать:**
1. **Фокус-режим:** двойной клик по механизму (или кнопка «Фокус» в его карточке) временно раскладывает участников: источники — колонкой слева, механизм — в центре, приёмники — колонкой справа. Остальные узлы — 20% прозрачности и не участвуют в физике на время режима.
2. В фокус-режиме на рёбрах — **подписи** с описанием передачи участника («Источник к-ва дней»). Длинные подписи обрезаются до 32 символов с многоточием, полный текст — в tooltip.
3. Выход из режима: `Esc`, повторный двойной клик, кнопка «Выйти из фокуса» над холстом. Узлы плавно (≤ 250 мс) возвращаются в **исходные** позиции (сохранённые перед входом), физика восстанавливается.
4. **Мини-карта** в правом нижнем углу над контролами холста: весь граф схематично + рамка видимой области; клик/перетаскивание рамки перемещает холст. Сворачивается. По умолчанию скрыта, если узлов < 30.

**Не делать:** сохранять фокус-раскладку в данные; менять глобальную физику.

**Критерии приёмки:**
- Вход в фокус-режим на механизме с 3 участниками: все источники левее механизма, все приёмники правее, подписи рёбер не пересекаются.
- После выхода позиции всех узлов совпадают с позициями до входа (погрешность ≤ 1px).
- Фокус-режим не записывает координаты в сохранённые данные (проверить: вход → перезагрузка страницы → исходная раскладка).
- Мини-карта синхронна с холстом при зуме и панорамировании; клик по ней перемещает видимую область.
