# Карта связей объектов — бриф для продолжения в Claude Code

## Что это

Локальный прототип (один self-contained HTML-файл) для проверки UX сервиса, который будет фиксировать связи между объектами конфигурации 1С — какие настройки где используются, как одно правило связывает несколько объектов. Полная спецификация целевого сервиса (бэкенд на Fastify + Prisma + PostgreSQL, фронт на React + graphology + sigma.js, Docker-деплой) лежит в `SPEC.md` рядом — прототип её сознательно упрощает, чтобы можно было потрогать UX руками до вложения в полный бэкенд.

## Принятые архитектурные решения — не пересматривать без явного запроса

- **Механизм как гиперребро.** Связь между объектами — не пара «откуда-куда», а отдельная сущность `mechanism` с участниками (`participants`), у каждого своя роль (`source` / `target` / `neutral` по направлению). Проекция в обычные рёбра для схлопнутого вида графа строится из этого правила (см. `buildGraph` в коде) — не заменяй на прямые пары.
- **Исходники разделены на файлы, для передачи собирается один HTML** (решение FT_16; раньше был один файл без сборки). Структура:
  ```
  src/index.html        разметка; открывается двойным кликом как есть (обычные <script src>, не ES-модули — с file:// модули не грузятся)
  src/css/tokens.css    токены темы (:root) — все цвета, размеры, прозрачности
  src/css/app.css       остальные стили
  src/js/core.js        справочники, состояние, утилиты, хранение, папка и вложения, CRUD
  src/js/graph.js       построение графа, физика, подсветка, подписи, отрисовка, мышь на холсте, switchView
  src/js/cards.js       правая панель: карточки объекта/механизма/ребра и их общие компоненты
  src/js/list.js        фильтр тегов левой панели и режим «Список»
  src/js/sidebar.js     левая панель, подсистемы и теги, редактор чипов
  src/js/search.js      поиск Ctrl+K, selectEntity, модальные окна
  src/js/canvas.js      ширины панелей, масштаб и вписывание, фокус-режим, подсказки, мини-карта, легенда
  src/js/roles.js       справочник ролей-исполнителей (процессы): CRUD, карточка роли
  src/js/attributes.js  реквизиты объектов: CRUD, проверка имени, блок «Реквизиты» в карточке объекта
  src/js/controls.js    ручные контроли: CRUD, карточка, обратные ссылки в карточках объекта и механизма
  src/js/main.js        resizeCanvas, обработчики, init
  build.js              node build.js → dist/nodus.html (один самодостаточный файл); --check — dist актуален
  tools/check.js        синтаксис JS, сверка id между JS и разметкой, актуальность dist
  ```
  Все JS-файлы — обычные скрипты с общей глобальной областью; порядок подключения в `src/index.html` = порядок в сборке. Каждый файл начинается с `'use strict';` и пустой строки (build.js это проверяет). Файлы разрезаны по разделам прежнего файла без перестановок: сборка FT_16 побайтно совпадала с `object-graph-prototype.html` v0.5.0. **После любой правки в `src/` — `node build.js` и коммит `dist/nodus.html` вместе с исходниками.** Node нужен только для сборки и проверок; пользователь открывает `dist/nodus.html` или `src/index.html`.
- **Формат данных** — `serializeState()` / `applyState()` в core.js, единственное место: localStorage, папка, экспорт, импорт, очистка. `formatVersion: 2`; разделы `roles`, `attributes`, `controls`, `tombstones` (и будущие разделы процессов) необязательны — файл без них читается как пустые коллекции.
- **Удалённые ссылки не исчезают.** При удалении сущности, на которую ссылаются (контроли, далее шаги процессов), её название запоминается в `tombstones` (`rememberDeleted`), а ссылка показывается как «⚠ Удалено: <название>» (`brokenRefHTML`).
- **Хранение данных — localStorage браузера**, плюс опциональное автосохранение JSON-снепшота в выбранную пользователем папку через File System Access API (Chrome/Edge only, требует явного выбора папки — API физически не даёт доступ к произвольному пути строкой).
- **Вложения к объектам/механизмам хранятся только в этой же папке** (не в localStorage, не в экспортируемом JSON — там только имя и размер файла). Требует подключённой папки; без неё — явное сообщение, а не тихий отказ.
- **Справочники (типы объектов, категории механизмов, роли участников) — константы в начале `<script>`**, не вынесены в UI-редактируемые настройки. Правятся прямо в коде.

## Что уже реализовано

- Force-directed граф на canvas (без внешних библиотек), два режима — «Объекты» (схлопнутый) и «Объекты и механизмы» (двудольный, механизм — отдельный узел-ромб)
- Ховер подсвечивает связи, клик фиксирует подсветку и открывает панель редактирования, клик по пустому месту снимает
- Полный CRUD объектов и механизмов, участники с поиском объекта по вводу названия (кастомный combobox, не нативный `<select>`)
- Вложения файлов (только при подключённой папке в Настройках)
- Поиск по названию/тегам, фильтры по типу объекта, тегу, категории механизма, статусу
- Настройки: где хранятся данные, подключение папки для автосохранения и вложений, переподключение при протухшем разрешении браузера
- Ресайзабельные боковые панели (drag-хендлы, ширина сохраняется в localStorage)
- Второй вид — «Список», плоский список объектов и механизмов, сгруппированный по типу/категории, с своим поиском и фильтром статуса
- Карточка объекта/механизма во всплывающем окне — **важно:** это не дублирующий код, а тот же `renderObjectPanel`/`renderMechanismPanel`, что и в боковой панели, просто вызванный с другим `panel`-контейнером (DOM-элементом). Не создавай отдельный шаблон для модалки — расширяй существующий, передавая параметр.

## Известные ограничения / не проверено вживую

- File System Access API (подключение папки, вложения) не тестировался в реальном браузере — только статическая проверка (`node --check`, сверка id между HTML и JS). Стоит проверить в Chrome/Edge на реальной машине пользователя в первую очередь.
- Нет автора/даты редактирования у объектов — пользователь присылал референс с колонками «Анна · 12.09.2026», но это не реализовано осознанно: в прототипе нет пользовательских аккаунтов, фабриковать несуществующие данные не стали. Если понадобится — это система timestamp'ов (`createdAt`/`updatedAt`), не multi-user identity.
- Отмена создания объекта через «+Создать» из комбобокса участника, когда сама форма механизма открыта в модалке-карточке, не восстанавливает карточку (только успешное создание восстанавливает). Известный, принятый на этом этапе компромисс, не баг.
- Нет автоматических тестов — только ручная проверка + статический анализ перед каждой выдачей файла.

## Правило, которое стоит унаследовать

Каждая выдача файла в этом проекте сопровождается `node --check` по JS и сверкой всех `getElementById(...)` в JS против реальных `id="..."` в HTML, чтобы не присылать файл с опечаткой в id, которую не видно на глаз. С FT_16 это делает `node tools/check.js` (вместе с проверкой, что `dist/nodus.html` пересобран). Запускать при каждой правке, а не только перед финальной сдачей.
