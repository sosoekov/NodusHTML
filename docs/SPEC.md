# Граф связей объектов конфигурации — техническое задание

## Роль

Ты — ведущий разработчик этого проекта. Работаешь этапами, после каждого этапа
показываешь работающий результат и ждёшь подтверждения. Не начинай следующий этап,
пока предыдущий не принят.

Если в задании что-то не определено — спроси, не додумывай. Особенно это касается
модели данных: она зафиксирована ниже, дополнительные сущности не изобретай.

## Что строим

Внутренний веб-сервис для небольшой команды (5–15 человек), который документирует
связи между объектами учётной системы: константами, документами, регистрами,
справочниками, обработками.

Пользователи вручную описывают, как настройки в одних объектах влияют на другие,
и потом получают ответы на вопросы:

- чем именно связаны объект A и объект B;
- что сломается, если изменить объект X;
- от чего зависит объект X.

### Ключевая идея модели

Связь — это не ребро между двумя объектами, а **механизм**, в котором участвует
несколько объектов, каждый в своей роли.

Пример. Механизм «Определение нормы срока подбора»:

- `Константа.НормаДнейПоиска` — роль «значение по умолчанию»;
- `РегистрСведений.НормыДнейПоискаПоГородам` — роль «переопределение»;
- `Документ.ЗаявкаНаПодборПерсонала` — роль «приёмник».

Описание механизма: значение берётся из константы, но если для города заявки есть
запись в регистре, она перебивает константу; результат попадает в реквизит
`СрокПодбора` документа.

Если разложить это на три попарных ребра, смысл теряется. Поэтому граф двудольный:
узлы-объекты и узлы-механизмы, участие объекта в механизме — ребро с ролью.

## Стек

Решения приняты, менять не нужно:

- **БД:** PostgreSQL 16
- **Бэкенд:** Node.js + Fastify + TypeScript, драйвер `pg`, миграции `node-pg-migrate`
- **Фронтенд:** React + TypeScript + Vite
- **Граф:** `graphology` (модель и алгоритмы) + `sigma.js` (рендер на WebGL)
- **Стилизация:** Tailwind
- **Аутентификация:** сессионная cookie, три роли (viewer / editor / admin)
- **Деплой:** docker-compose, один инстанс бэкенда

Redis не нужен: инстанс бэкенда один, pub/sub для SSE держится в памяти процесса.
Не добавляй ORM, очереди задач, микросервисы, GraphQL.

## Модель данных

```sql
-- Справочники. Редактируются только администратором, заполняются сидом.
-- Свободный ввод в этих полях запрещён: иначе три редактора заведут
-- «Регистр сведений», «РегистрСведений» и «Регистр сведений (независимый)».

object_types        (code PK, title, color, sort_order)
mechanism_categories(code PK, title, sort_order)
participant_roles   (code PK, title, direction)  -- direction: source | target | neutral

users (
  id, email UNIQUE, name, password_hash,
  role,             -- viewer | editor | admin
  created_at
)

objects (
  id            uuid PK,
  slug          text UNIQUE,          -- человекочитаемый, генерируется из full_name
  type_code     text REFERENCES object_types,
  name          text NOT NULL,        -- "Норма дней поиска"
  full_name     text,                 -- "Константа.НормаДнейПоиска"
  parent_id     uuid REFERENCES objects,  -- реквизиты, измерения, ресурсы
  subsystem     text,
  tags          text[],
  description   text,                 -- markdown
  status        text,                 -- stub | active | deprecated
  version       int NOT NULL DEFAULT 1,
  created_by, created_at, updated_by, updated_at,
  deleted_at    timestamptz           -- мягкое удаление
)

mechanisms (
  id            uuid PK,
  title         text NOT NULL,
  category_code text REFERENCES mechanism_categories,
  summary       text,                 -- до 200 символов, показывается на ховере
  body          text,                 -- markdown, подробное описание
  status        text,                 -- draft | active | deprecated
  version       int NOT NULL DEFAULT 1,
  created_by, created_at, updated_by, updated_at,
  deleted_at    timestamptz
)

mechanism_participants (
  id            uuid PK,
  mechanism_id  uuid REFERENCES mechanisms ON DELETE CASCADE,
  object_id     uuid REFERENCES objects,
  role_code     text REFERENCES participant_roles,
  note          text,                 -- чем именно участвует этот объект
  sort_order    int,
  UNIQUE (mechanism_id, object_id, role_code)
)

layout (
  object_id     uuid PK REFERENCES objects,
  x, y          double precision,
  pinned        boolean DEFAULT false
)

changes (
  seq           bigserial PK,         -- монотонный курсор синхронизации
  entity_type   text,                 -- object | mechanism | participant
  entity_id     uuid,
  op            text,                 -- create | update | delete
  payload       jsonb,                -- новое состояние сущности
  user_id       uuid,
  created_at    timestamptz
)

edit_locks (
  entity_type, entity_id, user_id, acquired_at, heartbeat_at,
  PRIMARY KEY (entity_type, entity_id)
)
```

Индексы:

- полнотекстовый (`tsvector`, русская конфигурация) по `objects(name, full_name, description)`
  и по `mechanisms(title, summary, body)`;
- триграммный (`pg_trgm`) по `objects.name` и `objects.full_name` — нужен для поиска
  похожих имён при создании, чтобы ловить дубли;
- обычные по `mechanism_participants(mechanism_id)` и `(object_id)`.

### Сид

Заполни справочники и создай фикстуру с примером из раздела «Ключевая идея модели» —
три объекта и один механизм. На ней проверяется весь пайплайн.

- `object_types`: Константа, Документ, Справочник, РегистрСведений, РегистрНакопления,
  Обработка, Отчёт, Роль, Подсистема, ОбщийМодуль, Реквизит, Измерение, Ресурс
- `mechanism_categories`: Расчёт, Заполнение, Проверка, Обмен, ПраваДоступа, Печать
- `participant_roles`: Источник (source), Приёмник (target), Параметр (source),
  Условие (source), Переопределение (source), ЗначениеПоУмолчанию (source),
  Участник (neutral)

## Инварианты

1. Удаление всегда мягкое. Жёсткое рвёт историю и ломает открытые вкладки у коллег.
2. Любая запись в `objects`, `mechanisms`, `mechanism_participants` в той же транзакции
   добавляет строку в `changes`.
3. Обновление — только оптимистичной блокировкой:
   `UPDATE ... WHERE id = $1 AND version = $2`, при нуле затронутых строк возвращается
   409 с текущим состоянием записи.
4. `parent_id` образует дерево максимум на два уровня: объект → его реквизиты.
   Реквизит реквизита не бывает.
5. Роли участников задают направление: `source → target`. На этом строится анализ влияния.

## API

```
POST   /api/auth/login
POST   /api/auth/logout
GET    /api/auth/me

GET    /api/graph/snapshot
GET    /api/changes?since=<seq>
GET    /api/events                      SSE

GET    /api/objects?q=&type=&status=&subsystem=&tag=
GET    /api/objects/:id                 полная карточка + механизмы по ролям
POST   /api/objects
PATCH  /api/objects/:id
DELETE /api/objects/:id
POST   /api/objects/bulk                массовая вставка списком
GET    /api/objects/similar?name=       поиск похожих имён (дубли)

GET    /api/mechanisms?q=&category=&status=
GET    /api/mechanisms/:id
POST   /api/mechanisms
PATCH  /api/mechanisms/:id
DELETE /api/mechanisms/:id
PUT    /api/mechanisms/:id/participants  замена всего состава разом

POST   /api/locks/:entityType/:id        взять мягкую блокировку
POST   /api/locks/:entityType/:id/beat   heartbeat, раз в 15 секунд
DELETE /api/locks/:entityType/:id

GET    /api/queue/incomplete             заглушки, объекты без связей,
                                         механизмы с пустым body

PUT    /api/layout                       сохранение координат
POST   /api/layout/recompute             пересчёт раскладки (admin)
```

### `/api/graph/snapshot`

Отдаёт весь граф разом и текущий `seq`. Только лёгкие поля — без `description`
и без `body` механизмов, иначе на 1000+ объектов ответ раздуется в десятки мегабайт.

```json
{
  "seq": 4821,
  "objects": [{ "id", "slug", "name", "type_code", "status", "tags", "parent_id", "x", "y" }],
  "mechanisms": [{ "id", "title", "category_code", "status", "summary" }],
  "participants": [{ "mechanism_id", "object_id", "role_code" }]
}
```

Тяжёлое содержимое подгружается по клику через `/api/objects/:id` и `/api/mechanisms/:id`.

### Синхронизация

Клиент получает снапшот и запоминает `seq`. Дальше держит SSE-подписку и применяет
приходящие патчи к своей копии графа в памяти. При обрыве связи на реконнекте
запрашивает `/api/changes?since=<последний seq>` и догоняет без полной перезагрузки.

Тот же журнал служит историей правок.

### Мягкие блокировки

При открытии редактора клиент берёт блокировку и шлёт heartbeat раз в 15 секунд.
Блокировка считается протухшей через 60 секунд без heartbeat.

Другие пользователи видят баннер «Редактирует Иван, 30 сек назад», поле открыто
в режиме чтения, есть кнопка «всё равно редактировать». Это не жёсткий запрет,
а предупреждение — совместное редактирование одного markdown-поля не поддерживается.

## Фронтенд

### Экраны

1. **Поиск** — стартовый экран. Строка поиска, фильтры по типу, подсистеме, тегам,
   статусу. Результаты — список с типом и полным именем.
2. **Карточка объекта** — боковая панель. Описание, реквизиты, и главное: список
   механизмов, где объект участвует, сгруппированный по ролям. Кнопки «локальный
   граф», «на что влияет», «от чего зависит».
3. **Редактор механизма** — заголовок, категория, summary, markdown-body с превью,
   таблица участников (объект, роль, примечание, порядок).
4. **Локальный граф** — граф вокруг одного объекта с ползунком глубины 1–3.
5. **Полный граф** — режим обзора со всеми фильтрами.
6. **Пути между объектами** — выбираются два объекта, показываются цепочки связей.
7. **Анализ влияния** — от выбранного объекта транзитивно по рёбрам `source → target`.
8. **Очередь незаполненного** — рабочий список для команды.

### Поведение графа

Это центральная часть, ей уделить больше всего внимания.

- **Наведение на узел** — подсвечиваются сам узел и все связанные с ним;
  остальной граф приглушается до 15% непрозрачности.
- **Клик по узлу** — подсветка фиксируется и держится, пока не будет клика
  по пустому месту. Клик по другому узлу переносит фиксацию на него.
- **Клик по пустому месту** — сброс фиксации.
- **Два режима отрисовки**, переключаются одной кнопкой:
  - *объектный* — механизмы скрыты, между их участниками нарисованы рёбра,
    на ховере ребра всплывает `summary` механизма;
  - *полный* — механизмы видны как узлы другой формы; сразу читается, что
    несколько объектов связаны одним правилом, а не несколькими независимыми.
- **Клик по ребру или узлу-механизму** — открывается панель с полным описанием.
- Цвет узла — по типу объекта, размер — по числу связей.
- Черновики (`status = draft`) отрисовываются приглушённо и полупрозрачно.
- Реквизиты по умолчанию свёрнуты в родительский объект, разворачиваются по кнопке.

### Раскладка

Координаты хранятся в БД. Не пересчитывай force-layout при каждой загрузке: на 1000+
узлов это долго, и картинка каждый раз получается разная — пользователь теряет
пространственную память о графе. Раскладка считается по кнопке администратором,
отдельные узлы можно закрепить руками (`layout.pinned`).

### Поиск путей и анализ влияния

Считаются на клиенте: полный список рёбер уже в памяти после снапшота, BFS
с ограничением глубины отрабатывает мгновенно. Отдельного эндпоинта не нужно.

Ограничения: глубина не больше 5, не больше 20 найденных путей. Каждый путь
показывается как цепочка «объект → механизм → объект» с summary механизмов.

## Ввод данных

Тысячу с лишним объектов заводят вручную. Здесь проект живёт или умирает, поэтому
эти требования не менее важны, чем граф.

- **Создание объекта прямо из редактора механизма.** Набираешь имя в поле участника,
  в выпадающем списке ничего нет — кнопка «создать» тут же, без ухода со страницы.
- **Заглушки.** Объект создаётся с именем и типом, всё остальное пусто,
  `status = stub`. Это нормальный рабочий режим, а не исключение.
- **Массовая вставка.** Textarea, куда вставляется список полных имён построчно;
  тип определяется по префиксу (`Документ.`, `РегистрСведений.`, `Константа.`);
  перед сохранением показывается разбор с возможностью поправить тип.
- **Защита от дублей.** При вводе имени — поиск похожих по триграммам, с
  предупреждением «возможно, вы имеете в виду…».
- **Шаблоны механизмов.** Пример из этого задания — типовой паттерн «значение по
  умолчанию с переопределением». Выбор шаблона расставляет роли участников,
  остаётся подставить объекты.

## Что не делаем

CRDT и совместное редактирование текста, импорт из внешних систем, комментарии,
вложения, мобильную вёрстку, публичный доступ без авторизации, экспорт в форматы
документов. Не добавляй это по своей инициативе.

## Этапы

1. Docker-compose, миграции, справочники, сид, аутентификация и роли.
2. CRUD объектов и механизмов с журналом `changes`, оптимистичной блокировкой
   и мягким удалением. API-тесты.
3. SSE, эндпоинт `/api/changes`, мягкие блокировки. Проверка: два браузера,
   правка в одном видна в другом.
4. Поиск, карточка объекта, редактор механизма, инлайновое создание объектов,
   массовая вставка, защита от дублей. **На этом этапе система уже полезна** —
   можно начинать наполнять базу.
5. Снапшот графа, локальный граф с ховером, фиксацией по клику и двумя режимами.
6. Полный граф с фильтрами, хранимая раскладка, поиск путей, анализ влияния,
   очередь незаполненного.

## Правила работы

- Один коммит на этап, осмысленное сообщение.
- Тесты — только на бэкенд: инварианты, версионирование, журнал изменений,
  мягкое удаление. Фронтенд тестами не покрывай.
- Все миграции — отдельными файлами, откатываемые.
- В `README.md` держи актуальную инструкцию запуска.
- Если по ходу дела упрёшься в противоречие в этом задании — останавливайся
  и спрашивай, не выбирай вариант молча.
